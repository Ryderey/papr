# Gitee 私有仓库作为个人 RSS 同步存储的调研

调研日期：2026-10-05。范围：个人使用 Papr 桌面端与 Android 端，同步订阅、文件夹、文章列表中的标题与链接、星标及稍后读；正文由各端获取，不同步主题、字体、AI 配置。本文只查阅官方公开文档，未调用用户账号、创建仓库、部署服务或修改业务代码。

## 初步判断

Gitee 私有仓库可以作为这一用途的候选存储。个人社区版的仓库数量与容量，足以支持先做小规模元数据同步验证；但容量并不能替代同步协议。Papr 仍需要实现跨设备稳定标识、合并、删除标记、离线重试和远端文章元数据导入。国内网络体验应以用户实际桌面与手机网络测试为依据，本次没有测量可用性或延迟。

与 GitHub 方案相同，这一方向由客户端抓取 RSS、把元数据写入私有仓库；它不会像 FreshRSS 服务端一样在两个客户端均离线时持续抓取文章。是否接受这一行为，是选择仓库存储还是 RSS 服务端的主要取舍。

## 已确认的个人社区版配额

Gitee 官方首页明确列出“私有仓库免费”；在当前个人社区配额内使用本方案无需企业套餐。免费服务与额度可能调整，不作永久承诺。[官方首页](https://gitee.com/indexpage)

[Gitee 官方产品配额说明](https://help.gitee.com/questions/Gitee产品配额说明)的“社区版（个人用户）”列出：

| 项目 | 官方配额 |
| --- | --- |
| 仓库数量 | 1000 个，不限制公有或私有 |
| 单个 Git 仓库 | 500M |
| 单文件 | 50M |
| 用户总仓库容量 | 5G，包含用户名下及其创建组织下的仓库 |
| 私有仓库协作人数 | 个人账号所有私有仓库合计 5 人 |

桌面和手机使用同一账号不应按两个协作者设计。用于同步的仓库应独立于 Papr 源代码仓库，避免读者数据与开发历史混合。这里只同步元数据、不保存正文和图片，有利于控制体积；实际可保存的文章数量仍取决于字段大小、保留范围和提交频率，不能据此承诺永久免费或无限存储。

容量监测须包含 Git 历史。官方说明超配额可能锁定仓库推拉服务，解除方式包括升级或改写历史；只删除当前分支里的旧文件不能作为历史已释放的保证。后续设计应避免每次阅读状态变化都重写大型完整快照，并明确文章保留及历史维护策略。[产品配额说明](https://help.gitee.com/questions/Gitee产品配额说明)、[仓库体积过大，如何减小](https://help.gitee.com/questions/仓库体积过大，如何减小)。

## API 限流：尚未获得官方明确额度

本次检索 Gitee 官方帮助中心、API 文档与公开 Swagger，未找到可以确认个人账号认证请求额度、写入请求额度、突发限制或重置周期的现行官方说明。公开 [API 文档](https://gitee.com/api/v5/swagger)及 [Swagger JSON](https://gitee.com/api/v5/swagger_doc.json)可以核实接口字段，不能据此推导出限流额度。

因此不能把 GitHub 的每小时额度套用到 Gitee，也不能以网上出现的“60 次”“5000 次”等数字作为实现依据。这是本次未确认项，不代表 Gitee 没有限流。

如后续实施，先采用低频拉取、前台或主动同步、批量合并本地变化、错误退避；不要为每次点击立即发起独立写请求。再通过经用户授权的账号集成测试，记录响应状态及可用限流头，确认读写边界和失败恢复行为。本轮没有做此测试。

## OAuth 与私人令牌的权限粒度

可以确认 Gitee 提供 OAuth 文档入口与私人令牌。官方镜像管理文档明确展示了“用户头像 → 设置 → 私人令牌”，并要求该镜像操作使用包含 `project` 权限的 Gitee 令牌。[OAuth 文档](https://gitee.com/api/v5/oauth_doc)、[官方镜像管理文档中的 Gitee 私人令牌章节](https://help.gitee.com/repository/settings/sync-between-gitee-github#1-申请-gitee-的私人令牌)。

这份镜像指南含有截至 2022 年的旧说明，其 `project` 示例只证明对应功能曾要求该类权限。它不充分证明当前 Contents API 应选哪个 scope，也不证明令牌能收窄到单个仓库、仅文件读写、读写分别授权或设置有效期。指南另一些段落中的 `repo`、`admin:repo_hook` 明确属于 GitHub 令牌，不应当当作 Gitee 的权限清单。

当前公开 OAuth 页面通过本次文本抓取仅返回页面框架；公开 Swagger JSON 的 `securityDefinitions` 为空，未提供可验证的完整 OAuth scope 定义。本次无法确认 Gitee 是否具备与 GitHub fine-grained PAT 等价的“单仓库 + Contents 读写”权限粒度，也未确认桌面与 Android 公共客户端所需的 PKCE 支持、刷新与撤销行为。应保留为后续授权设计验证项，不宣称不存在这些能力。[官方 OAuth 入口](https://gitee.com/api/v5/oauth_doc)、[官方 Swagger JSON](https://gitee.com/api/v5/swagger_doc.json)。

个人使用初期可以评估手动配置专用私人令牌的可行性，前提是明确实际可授予的最小权限；令牌保存在各端安全存储，不能写入同步仓库、提交历史或日志。如果令牌只能获得较宽权限，再评估专用同步账号等隔离办法。不要把需要保密的 OAuth 客户端密钥放进可分发的桌面或 Android 安装包。

## 尚未验证与后续边界

本轮确认的是官方文档中的配额和已公开的令牌示例，没有完成账号层面的功能验证。限流数字、权限收窄范围、OAuth 公共客户端适配及实际网络稳定性仍未确认。Contents 接口的读取、写入及并发条件见下文；即使接口支持 SHA 前置条件，也仍需由 Papr 处理冲突后重拉、重新合并和重试。

实现前至少验证：两端同时更新、离线后重连、写请求超时后的重复提交、删除与另一端修改同时发生、令牌失效、仓库接近配额。上述均为未来实施验证项，本次只做静态调研，未运行业务测试。
## 文件 API 与并发同步判断

主调研于 2026-10-05 只读获取了官方机器可读接口定义，info.version 为 5.4.93。未访问私人仓库或提交数据。[官方 Swagger](https://gitee.com/api/v5/swagger)、[公开接口 JSON](https://gitee.com/api/v5/swagger_doc.json)

确认：
- GET /api/v5/repos/{owner}/{repo}/contents/{path} 获取文件，可指定 ref（分支、tag 或 commit）。
- POST 同一路径新建文件；PUT 更新文件。新建与更新不同，不是简单把 GitHub 域名替换成 Gitee。
- PUT 必须提供 content（Base64 编码）、message 和旧文件的 Blob SHA；SHA 从文件查询取得。
- POST /api/v5/repos/{owner}/{repo}/commits 可提交多个文件变更，actions 支持 create/delete/move/update/chmod；可填写每文件最近提交的 last_commit_id。公开定义不足以证明其完整事务与并发失败语义，不能据此直接承诺多文件原子同步。
- 所读 JSON 中 securityDefinitions 缺失，不能从这个文件推导精细授权能力或认证限流数值。

基于这些接口，可以设计与 GitHub 方案相同的数据模型：订阅/文件夹稳定 ID，文章标题/链接/日期，独立星标/稍后读（可附带已读），以及删除标记。正文和设备设置不上传。Papr 各端仍独立抓取 RSS；Gitee 存放目录与状态，不负责全天发现文章。

同步应保留“上次已确认快照 + 持久化本地改动”，读取远端后按字段合并，再携带旧 SHA 写入。电脑加星标与手机加稍后读应同时保留，取消状态和订阅删除也必须传播。不能整份最新本地 JSON 覆盖远端，也不能只在写入前额外读一次就称为并发安全。官方定义要求旧 SHA，但没有完整描述过期 SHA 的响应和批量提交冲突语义：实施前需要用独立测试仓库验证服务器拒绝过期版本、首建竞争和失败重试。当前调研未作此真实写入验证。

## 对 Papr 的建议与开发范围

在“仅个人、电脑与 Android 都用 Papr、只同步元数据和状态、优先国内网络、免服务器运维”这个范围内，Gitee 是可行候选，可以排在 GitHub 前面进行连接与并发验证。国内网络优势来自用户使用场景，本轮未在其电脑和 Android 网络做延迟/成功率测试，不承诺全国或所有运营商都更稳定。

当前 Papr 没有 Gitee 同步提供方。需要新增提供方、文章元数据上传/导入、独立 read_later 双向传播、文件夹/订阅生命周期、冲突合并、持久化待发队列与失败恢复。桌面和 Android 的两条实现要保持一致。可复用与 NewsNook 类似的可靠性设计，不需要搬入其账号服务器与 PostgreSQL，也不需要启动现有腾讯云服务器。[完整客户端缺口](docs/personal-rss-sync-options-2026-10-05.md:25)

配置上建议专用私有仓库与专用同步凭据，保存到各端安全存储；实际可授权范围以 Gitee 当前设置和验证结果为准，不能照搬 GitHub fine-grained PAT 的单仓库 Contents 权限承诺。API 文档存在 access_token 查询/表单参数，实现应避免令牌落入 URL 日志或诊断输出，并在接入时核对支持的认证传递方式。

仓库数据应分成少量逻辑文件并批量提交，普通文章定义保留范围，星标与稍后读条目长期保留。Git 历史也占容量，当前快照体积并不代表长期仓库体积；超配额后的瘦身涉及历史改写，不能作为自动日常动作。正文不上传，故原站删文后的全文可用性无法保证。

本轮仅新增本调研文档，没有修改业务代码、创建仓库、使用账号凭据或部署服务。读取公开 API 定义不等于验证私人仓库读写；采用前需验证实际网络、认证权限、过期 SHA 拒绝、离线合并、取消状态及文章目录完整导入。
